## 3. 三值语义

结论只有三种：**支持 / 不支持 / 无法确认**。

- **无证据不等于不支持**：没有检索到候选、候选证据不足、模型不可用时输出无法确认，
  并记录缺口原因。
- **不支持必须有明确否定/限制**：只从 `content.limitations` 的已审核断言取否定证据，
  要求 `limitations.N` 断言证据存在且范围重叠达到阈值；单纯数值低于阈值不判不支持，
  只作为上下文。
- **冲突未解决则无法确认**：同一要求同时存在支持证据和明确否定/限制证据时，
  不擅自选边。
- **空阈值/开放枚举/强制状态不确定**：`blank_threshold`、`logic_ambiguity`、
  `open_enumeration`、`mandatory_status=uncertain` 均锁定无法确认，禁止猜测。
- **证明材料要求**：沿用 P2.1 的过滤结果，证明材料/截图/检测报告/证书/承诺函/商务列
  不进入技术参数；同一参数中的技术能力文本保留。P2.2 不把投标材料要求当成产品能力支持。

## 4. 确定性聚合

参数结论只由 `logic.aggregate_parameter` 按 P2.1 `logic_tree` 计算，
模型不能直接给出参数结论。

已覆盖：

- AND / AND_OPEN：任一不支持则不支持；否则任一无法确认则无法确认。
- OR / OR_OPEN：任一支持则支持；全部不支持才不支持；否则无法确认。
- AT_LEAST / MINIMUM：给定最小数量时按“支持数 + 无法确认数”判断达成、
  不可能或证据不足；缺少最小数量则无法确认。
- OPTIONAL：不参与必要聚合，但原子结果仍单独保存。
- 缺树、未知关系、非法节点、缺少原子结果：无法确认。
- 参数结论严格一条；原子条款单独评估，不增加顶层结论数量。

## 5. 固定发布与证据

任务创建时固定：

- `publication_id`
- `published_snapshot_id`
- `publication_hash`
- 参数与原子要求快照

运行和重试只读该固定发布。已通过测试验证：

- 管理员之后发布新版本，不改变已完成/运行中任务的结果与固定发布 ID。
- 发布 payload 被篡改：任务失败关闭，错误码 `PUBLICATION_TAMPERED`。
- 恢复发布后重试：从检查点恢复并成功。
- 发布不可用、快照状态异常、类别不一致：失败关闭，不静默切换当前发布。

证据链：

1. 只接受 `product_function` / `technical_mechanism` 且
   `review_status=human_accepted` 的已审核能力。
2. 从服务端发布清单和 ClaimRevision 校验修订、声明类型和审核决定。
3. 模型只能引用服务端给出的证据 ID；伪造 ID、候选 ID 或引文被拒绝。
4. 来源文件按固定快照路径回读，校验文件 SHA-256、行范围和引文哈希。
5. 文档证据回读分段与原始文档，校验文档哈希/分段哈希；敏感分段和测试来源被排除。
6. 审计不记录招标全文、源码或模型输出，只记录哈希、计数和错误码。

本次已新增**文档来源**集成用例：文档审核发布后，评估结论使用 `kind=document`
的已核验证据，验证通过。

## 6. 模型边界

- 复用 Pydantic AI 与 `configured_model`。
- 输出严格 Pydantic 校验；模型只判断单个原子要求。
- 模型只能改写确定性结果为“无法确认”的原子；确定性“不支持”不能被模型推翻。
- 支持判断必须有非空理由，且 `equivalence` 不能为 `insufficient`；
  必须指定为具体机制而模型给出 `different_mechanism` 时拒绝。
- 请求/Token/上下文/批量大小有界；预算耗尽降级为无法确认，并记录
  `EVALUATION_MODEL_BUDGET_EXCEEDED`，不伪造支持。
- 无管理员工具、无未发布知识、系统提示明确招标文本是不可信数据。


## 10. 失败与修复记录

### 10.1 真实 PostgreSQL 首次失败

首次运行日志：`docs/acceptance/p22_postgres_fail.log`。
表现为任务 `partial`、5 个参数全部 `EVALUATION_PARAMETER_ERROR`、9 个原子全部
`failed_closed`。

根因是两处 ID 长度契约小于真实 ID：

- 真实证据 ID 为 `ev-` + 64 位 SHA-256，共 67 字符；评估证据列原为 64。
- 真实候选 ID 形如 `p14-<uuid>-0`，超过原模型的 36 字符上限。

SQLite 不强制 VARCHAR 长度，所以此前未暴露；PostgreSQL 在写入时拒绝。修复为：

- `evaluation_evidence.evidence_id/capability_id/revision_id` 统一 VARCHAR(80)，
  模型与迁移同步。
- `EvidenceAnchor.evidence_id`、`ModelJudgment.capability_id/evidence_ids`
  扩大到 80，并增加 67 字符证据 ID、42 字符候选 ID 的回归断言。

修复后真实 PostgreSQL 测试通过，保留失败日志用于追溯。

### 10.2 参数与逻辑树绑定修复

P2.1 提取期 JSON 中的 `requirement_id` 与 `TenderAtomicRequirement` 表主键不同，
早期按 ID 回查导致叶子失配、参数被强制无法确认。现由服务端按原文/顺序重新绑定，
并重映射逻辑树叶子；5/15 参数用例已覆盖。
