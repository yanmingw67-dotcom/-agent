# P1.5实施计划

依据原设计书§1.2、§7、§9.1、§11 AC-14/16、§12 P1.5及本轮启动指令。
基线f2a43329ef353ebef13747ca0ea0a8d5219bae72。原迁移、测试、报告和业务记录保留。

1. 实现POST /api/v1/probes，输入仅category_id、单条requirement_text及有界limit。
   检索服务端口8001执行，后台API端口8000不执行Probe检索。
2. PostgreSQL独立REPEATABLE READ READ ONLY事务内绑定品类当前发布/快照双指针。
   不接受用户版本/快照参数；返回内部追溯标识不是版本选择功能。
   请求开始后切换不混读，下个请求读取新指针；无需加品类写锁。
3. 只读取冻结发布清单和审核记录，不把模型草稿作为事实源。
   当前清单中的旧批准修订若已有更新修订，Probe保守隐藏并返回缺口；
   不自动采用尚未发布的新批准修订。P1.4历史冻结payload保持不变。
4. 检索为确定性词法匹配，不调用模型、不作符合性判定或等效推断。
   原样保留描述、scope、conditions、limitations、断言、证据、审核来源、覆盖缺口。
   possible_equivalent明确hypothesis，不能变成满足。
5. 返回前复验同快照证据来源哈希和修订/清单关联。失效证据对应条目不作为结果，
   返回结构化缺口；空库/未发布/无命中/未知均不等于不支持。
   返回条目数量、证据数量、耗时及完整响应大小有界，超限不裁掉能力边界。
6. 复用原Pydantic AI自主探索与静态索引，不新增Agent B、模型网络调用或自动审核入口。
   全链路使用公开人工样例及FunctionModel；明确Mock与既有真实模型来源的区别。
7. 增量测试包括最新修订、未审未发、跨产品、证据损坏、发布切换、回滚与只读事务。
   实际Compose执行上传→解压→索引→自主探索→证据→显式审核→发布→Probe。
8. 对比空闲与真实Builder运行期间Probe P50/P95，采集CPU/内存、并发与样本数。
   保持原4 CPU/6144 MiB容器配额、单builder、独立检索通道/队列。
   开发Docker环境不是独立4C8G虚拟机；公开小样例不是企业真实规模性能证明。
9. 交付P1.5变更说明、端到端/性能/安全证据、运行手册及剩余问题。
   本轮明确要求提交代码，未明确授权再次push；创建本地提交并暂停等待审核。
