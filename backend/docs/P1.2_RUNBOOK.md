# P1.2 运行与复验

## 第一轮整改复验补充

最新迁移0004，旧源码状态按最近真实source_index任务恢复；请备份数据库后依原命令升级，
不要重写0001～0003或删除数据卷。旧文档解析结果不会在迁移中凭空修复；
暂存快照显式build会按p12-2重新解析。已发布快照保持不可变，后续应走新快照/发布流程。

整改专用：`uv run python -m scripts.p12_remediation_acceptance`。
原基准新增REPORT_DIR支持，复跑使用
`REPORT_DIR=reports/p12-remediation uv run python -m scripts.p12_acceptance`，
不覆盖reports/p12历史原始数据。

索引状态仅指源码；文档状态查看GET /snapshots/{id}/documents，
parse_details.pages包含页号和parsed/empty_page/ocr_required，
parse_details.sheet_merged_ranges包含Sheet级合并范围。partial文档的可解析页可正常搜索/回读。

工具响应须同时检查coverage_incomplete、truncated和warnings；
无命中且coverage_incomplete=true时不能据此作出不支持结论。
超时且next_cursor未推进时应停止机械翻页，缩小查询/模块范围或调整执行预算后重试；
成功翻页必须保持查询/过滤不变，重建索引后从cursor=0重新开始。
`index_status=indexed`不代表所有语言AST/超限文件/OCR或文档都已完整覆盖，更不代表已发布。


## 安装/部署

需要 Python3.12+、uv、Docker Compose。不要覆盖已有 .env，不要删除已有数据卷。

```sh
cd backend
uv sync --frozen
# 仅全新环境执行；已有 .env 跳过
uv run python scripts/generate_env.py
docker compose up --build -d --wait --wait-timeout 180
docker compose ps
docker compose exec -T api alembic current
docker compose exec -T api alembic check
```

保持原 Compose project 名以保留 P1.1 数据；api 启动运行迁移到0003。
API 端口8000；独立 retrieval 端口8001；均仅监听127.0.0.1。
生产需 TLS 反代。服务依赖与资源限额见 P1.2_ARCHITECTURE.md。
源码只读 indexer 不挂载归档卷，勿为了“修复权限”添加归档或源码写权限。

如修改资源/安全限额，在 docker-compose.yml environment 中显式设置；
Compose 不会自动把 .env 的所有变量传入容器。.env.example 列出本地运行配置。
配额默认10GiB（归档/解压/技术文档），预留 free1GiB，不含数据库/镜像。
索引单文件默认2MiB，大文件元数据保留但不AST/关键词索引。
调整配额前检查 GET /api/v1/admin/storage。

## 使用流程

所有接口使用 Authorization: Bearer ADMIN_TOKEN / READ_TOKEN，不把真实 Token 写入命令日志。

1. POST /api/v1/categories 建立品类；POST /categories/{id}/source 以 multipart file 上传 ZIP。
2. GET /jobs/{job_id} 等待 stage=extracted。
3. POST /snapshots/{snapshot_id}/build →202，新 source_index 任务到 stage=indexed。
4. POST /categories/{id}/documents，以 multipart 提供 snapshot_id 和 file，
   自动创建 document_index 任务。支持 PDF/DOCX/XLSX/MD/TXT。
5. GET /snapshots/{id}/documents 查询 parse_status/error_code。
6. POST 到 **8001** /api/v1/retrieval/{category_id}?snapshot_id={id}，
   管理员暂存检索 JSON 如：
   `{"tool":"search_symbols","query":"RobotSender.send","limit":30}`
   或 `{"tool":"search_code_batch","queries":["sender.send"],"mode":"literal","limit":30}`。
7. read_source 用 file_id/start_line/end_line 或 symbol_id；
   read_document 用 search_documents 返回的 segment_id（响应 item.id）。
   共享工具不接收品类/快照字段，作用域由 HTTP 路由和已鉴权角色在服务端绑定。
8. 工具返回 envelope，必须检查 truncated、warnings、next_cursor；
   分页时将 next_cursor 转成整数放入下一次 cursor。
9. 普通 read 不能带后台 snapshot_id，只按品类 active_snapshot_id 查询；
   P1.2 尚无发布流程，尚未发布时返回409 KNOWLEDGE_NOT_PUBLISHED。
   不要为了演示方便将暂存快照直接标记 published。
10. 失败/partial 任务可 POST /jobs/{id}/retry；逐文件检查点保留，同快照相同哈希/版本跳过。
    不会把 retry 等同于修复非法文档；修正内容后应作为新上传记录提交。

未发布状态与 index_status 分开；indexed 不等于能力画像或发布成功。
暂存查询只供管理员调试。Agent A/B、本期证据 ID、能力事实、Probe均未实现。

## 检查及端到端基准

```sh
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
# 全新检出后若需重建人工资产
uv run python -m scripts.generate_p12_fixtures
# 六服务已健康后执行；会新增人工品类/快照，不删除已有数据
uv run python -m scripts.p12_acceptance
```

基准默认600个额外代码文件，总607条文件索引；可用 BENCH_FILES 调整，不应超过ZIP安全限额。
脚本先验证小样例索引和三类文档，再在另一个品类建大索引，同时请求已索引小品类的检索通道，
对应未来“后台新知识建设不阻塞已有知识交互”的路径。不是同时查尚未索引的完整新库。
P50/P95 是实际 HTTP 往返延迟，原始样本、进程/容器采样、配额、路径定位均写JSON。
基准文件在 reports/p12；如重跑需自行指定新工作副本或先保存旧结果，避免覆盖审查证据。
不使用模型或Mock索引；测试有明确模拟故障用例，不冒充真实网络/断电验证。

基本指标：8000和8001的 GET /api/v1/admin/metrics（管理员）。
分别含该服务进程的HTTP/检索及DB查询延迟，重启清零；任务指标看 /jobs/{id}。
监控平台仍需关注 PostgreSQL/Redis 数据卷和宿主机磁盘，不存在自动邮件/告警发送服务。

## 恢复/孤儿盘点

GET /api/v1/admin/storage 仅扫描，不删除；结果有 quota/used/reserved、
引用/inflight_protected/orphan_candidate、truncated。
进程崩溃可留下预留或临时目录，系统保守拒绝超额新导入；请先停止写入并核对数据库任务、
备份卷和预留账本，再经管理员审批维护。未提供自动清理或一键释放接口。
不能按mtime或孤儿候选标志直接删除当前/审核证据，尤其不能 docker compose down -v。

## 已知降级

- 支持AST：Python/Go；其他语言文本检索+unsupported。
- 支持UTF-8与带BOM UTF-16/32；异常编码明确标记；不自动猜测GBK等全部编码。
- 语法引用是候选，不是准确语义调用图；模块/入口未做业务审核。
- PDF扫描件ocr_required；OCR不在本批；复杂表格/嵌入对象不保证重建。
- 敏感启发式可能漏报，真实源码仍需企业安全策略。
- 独立4C8G虚拟机尚需部署方复跑；开发侧为4核总配额/8GB预算内容器验证。
