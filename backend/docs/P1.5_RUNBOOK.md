# P1.5 运行手册：只读 Knowledge Probe

本手册对应 P1.5 的 Compose 验收环境。P1.5 只增加只读 Probe，不进入 Agent B，
不新增模型调用、审核或发布写入。所有命令在本目录（`backend/`）执行。

## 1. 前置条件

- Docker Engine + Compose，Python 3.12+（推荐 uv）。
- `.env` 已由 `scripts/generate_env.py` 生成；至少包含不同的
  `ADMIN_TOKEN`、`READ_TOKEN` 与 `POSTGRES_PASSWORD`。不要把 `.env`、
  token 或企业源码提交到 Git。
- P1.3 真实模型记录 `reports/p13-autonomous/real-compact-final.json` 与
  P1.4 发布记录 `reports/p14/round1/real-api-postgres-success.json` 存在。
- 目标品类当前生效发布应为 P1（`1af83dd5-e04e-4517-a81c-ab8a15201280`）；
  P1.5 验收脚本会在异常时尝试恢复 P1。

P1.5 的验证脚本不需要真实模型 Key；不要为了跑 Probe 配置或调用模型。

## 2. 启动与健康检查

```sh
cd backend
uv sync --frozen
uv run python scripts/generate_env.py   # 仅当 .env 不存在；已有 .env 不要覆盖
docker compose up --build -d --wait --wait-timeout 180
docker compose ps
```

预期：`api`、`worker`、`indexer`、`builder`、`retrieval`、`postgres`、
`redis` 均为 running/healthy。API 在 `127.0.0.1:8000`，检索服务在
`127.0.0.1:8001`。数据库与 Redis 不映射到主机端口。

若使用本地 `.venv` 而不是 uv，可用 `.venv/bin/python` 替代
`uv run python`；测试依赖与锁定版本见 `pyproject.toml`。

## 3. Probe 契约

```http
POST http://127.0.0.1:8001/api/v1/probes
Authorization: Bearer <READ_TOKEN 或 ADMIN_TOKEN>
Content-Type: application/json

{
  "category_id": "<category_id>",
  "requirement_text": "事件 预览 模式 分发 筛选",
  "limit": 10
}
```

- 只接受 `category_id`、`requirement_text`、`limit`；额外字段、查询参数、
  空白输入、`limit` 越界均返回 422。
- `limit` 默认 10，范围 1–20。
- 只使用品类当前生效发布；不接受 `snapshot_id`、`publication_id` 等覆盖参数。
- 成功响应只表示“候选检索”，不是满足/合规结论：
  `formal_compliance_decision=null`、`support_status=not_assessed`。
- 未发布品类返回 409 `KNOWLEDGE_NOT_PUBLISHED`；未知品类返回 404；
  匿名/错误令牌返回 401；访问后台 API 的 Probe 返回 503。

最小只读检查（不打印 token）：

```sh
set -a; . ./.env; set +a
curl -sS -X POST "http://127.0.0.1:${RETRIEVAL_PORT:-8001}/api/v1/probes" \
  -H "Authorization: Bearer ${READ_TOKEN}" \
  -H "Content-Type: application/json" \
  -d '{"category_id":"76d40f66-1c3e-487d-9a67-47d84da8fa69","requirement_text":"事件 预览 模式 分发 筛选"}' \
  | jq '{status,publication_id,publication_hash,candidates:[.candidates[].capability_id],gaps:[.unverified_gaps[].code],formal_compliance_decision,support_status}'
```

预期 P1：`status=candidate_retrieval`，发布 ID
`1af83dd5-e04e-4517-a81c-ab8a15201280`，哈希
`877338d1623d38d6e913b19634f57dee69183e28c5afa9069028612b501d0f90`，
至少 1 个候选，包含 `REQUIREMENT_COMPLIANCE_NOT_ASSESSED` 与
`KNOWLEDGE_COVERAGE_INCOMPLETE` 缺口，`formal_compliance_decision=null`，
`support_status=not_assessed`。

## 4. 验收命令

在 `backend/` 下执行，输出写入 `reports/p15/`；脚本都会拒绝覆盖同名 JSON，
重跑时请使用新的 `--label`。

### 4.1 Compose 端到端验收

```sh
uv run python scripts/p15_acceptance.py --label compose
```

覆盖：P1 读取与证据逐字段回读、匿名/错误令牌/管理员权限、严格输入校验、
后台 API 503、检索服务无写路由、未知品类 404、新品类上传→索引→未发布 409、
P1.3 历史真实模型任务可读、P1→P2→P1 发布切换与精确复原。预期输出
`passed=true, checks=44, steps=25`，证据为
`reports/p15/p15-acceptance-compose.json` 与对应 `.log`。

脚本会创建一个新的本地测试品类/快照（人工公开 ZIP），不会删除既有数据；
该品类保持未发布，不改变 P1 生效状态。结束时应保持 P1。

### 4.2 Probe 性能基线（空闲 + 合成 Builder 负载）

```sh
uv run python scripts/p15_benchmark.py --label compose
```

先测空闲单并发/4 并发，再在 `builder` 配额内启动一个 45 秒的 CPU 自旋 +
PostgreSQL 只读计数负载，同时测 4 并发和单并发。该负载是合成负载，不调用模型，
不代表真实 Agent A 语义。预期 `passed=true, errors=0`，证据为
`reports/p15/p15-probe-benchmark-compose.json`、`.log` 和
`p15-builder-load-compose.log`。

### 4.3 真实 Agent A 运行时下的 Probe（FunctionModel）

```sh
uv run python scripts/p15_agent_load.py --label compose
```

流程：停止 `builder` 容器并确认无 running 实例 → 在未发布的测试快照上排队一个
知识任务 → 注入一次性本地派发令牌 → 在一次性 `builder` 容器内用
`FunctionModel` 执行真实 `run_builder` 运行时 → 同时对 **已发布的 P1** 压测
Probe → 恢复 `builder`。

- 该脚本只用于隔离测试环境；它会直接更新排队任务的 `dispatch_token`，
  不能在生产/共享环境运行。
- 作业记录标记为 `model_mode=TEST_FUNCTION_MODEL`；不是真实模型能力验收，
  不计模型费用。
- 若中途失败，脚本的 `finally` 会尝试 `docker compose start builder`；
  仍应人工检查 `docker compose ps`，并把遗留的 queued/running 测试任务标记为失败，
  避免真实 worker 误领取。
- 依赖 `reports/p15/p15-acceptance-compose.json` 中的新品类/快照；
  应先完成 4.1。
- 预期 `passed=true, errors=0`，Probe 全部 200，作业状态为
  `partial` 或 `succeeded`，`model_mode=TEST_FUNCTION_MODEL`；证据为
  `reports/p15/p15-probe-agent-load-compose.json`、`.log` 与
  `p15-agent-load-compose.log`。

`scripts/p15_builder_functional_load.py` 是该脚本在一次性容器内调用的内部入口，
不应单独运行；它要求队列中已有带本地令牌的任务。

## 5. 测试与静态检查

```sh
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

标准 pytest 不连接真实 PostgreSQL/Redis；真实 PG 测试会 skip，原因记录为
“需显式真实PostgreSQL测试环境”。在 Compose 内执行真实 PG 测试：

```sh
docker compose run --rm --no-deps \
  -e P14_RUN_POSTGRES=1 \
  -v "$PWD/tests:/app/tests:ro" \
  api python -m unittest tests.infrastructure.test_p15_postgres -v
```

预期 `Ran 18 tests ... OK`（包含 P1.4 8 项与 P1.5 10 项）。
`P14_RUN_POSTGRES` 是沿用 P1.4 的显式开关名称，不是只跑 P1.4。

## 6. 发布切换与回滚

P1.5 不新增发布接口；发布/回滚使用既有管理接口：

```http
POST /api/v1/categories/{category_id}/rollback
Authorization: Bearer <ADMIN_TOKEN>
Content-Type: application/json

{
  "publication_id": "<目标发布ID>",
  "expected_active_publication_id": "<当前发布ID>",
  "comment": "P1.5验收切换"
}
```

P1.5 验收执行 P1 → P2 → P1，并验证：
- P1：1 个候选，哈希 `877338d1...`；
- P2：3 个候选，哈希 `2ba20577...`；
- 回到 P1 后除 `duration_ms` 外响应逐字段一致。

回滚是管理写操作，不属于 Probe；检索服务上这些写路由返回 404。

## 7. 资源、降级与故障排查

| 现象 | 检查/处理 |
|---|---|
| 8000 端口 Probe 返回 503 | 应调用 8001 检索服务；这是设计要求 |
| 409 `KNOWLEDGE_NOT_PUBLISHED` | 品类尚无生效发布；不要解释为不支持 |
| 409 `PUBLICATION_POINTER_INVALID` / `PUBLICATION_TAMPERED` | 指针或清单不一致；检查发布记录，不要绕过 |
| 401 | 令牌缺失/错误；使用 `.env` 中 read/admin 令牌，不打印 |
| 404 | 品类/路径不存在；确认 `category_id` 与检索服务端口 |
| 422 | 额外字段、查询参数、空白或 limit 越界；按契约修正 |
| 413 | 清单/证据/响应超限；不要要求 Probe 截断为不完整结果 |
| Probe 延迟升高 | 查看 `docker stats`、retrieval/builder/postgres 配额与并发；先确认没有真实构建任务争抢 |
| Agent 负载脚本失败 | 检查 `p15-agent-load-compose.log`；恢复 `builder`；将遗留测试任务标为失败 |
| 服务不健康 | `docker compose ps`；`docker compose logs --tail=100 api retrieval` |

资源配额：api 0.5 CPU/512 MiB，retrieval 1 CPU/768 MiB，builder 0.5 CPU/1024 MiB，
postgres 0.75 CPU/1536 MiB。Compose cgroup 配额不是独立 4C8G 虚拟机实测。

## 8. 停止与清理

```sh
docker compose stop
# 保留证据与数据，不要执行 docker compose down -v
```

验收会留下本地测试品类/快照、任务与报告，这是可追溯证据；不要在未确认时删除。
P1.5 不修改已有 P1.1～P1.4 业务数据、迁移或验收记录。
