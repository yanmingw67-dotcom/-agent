# P3.1-B 管理员真实资料上传指南

- 适用对象：中国区产品知识管理员、授权验收负责人
- 适用环境：P3.1-B 独立验收环境 `product-knowledge-p31b`
- 管理员页面：`http://127.0.0.1:18180/#/admin`
- 重要边界：本指南只说明管理员操作；Coding Agent 不搜索、不下载、不代传真实源码或正式文档
- 当前状态：Gate 2、Gate 3 仍 BLOCKED，完成本指南后必须重新执行关口核查

## 一、开始前确认

必须同时满足以下条件，缺一项都不要开始真实资料上传：

1. 已获得真实 WAF 源码 ZIP 与正式技术文档的**内部使用与验收授权**。
2. 已确认资料可以在本机独立验收环境处理，不上传到未授权的外部服务。
3. 企业数据模型外发授权已按公司流程完成；未完成时只能做上传、校验、确定性解析和本地索引。
4. 验收机至少有 15 GiB 可用磁盘；Docker 构建缓存较大，空间不足会中断镜像或索引任务。
5. 已从验收负责人处取得管理员令牌；不要把令牌写入聊天、工单、截图或日志。

## 二、启动并检查环境

在仓库 `backend/` 目录执行：

```bash
cd backend
P31B_IMAGE_TAG=6b8772b scripts/p31b_env.sh status
```

期望看到：

- 9 个服务 running/healthy；
- `alembic_head=0012`、`database_version=0012`；
- api、worker、indexer、builder、retrieval、taskworker 路径一致且非软链；
- 四个 worker 心跳新鲜；
- `P31B_ENV_STATUS=PASS`。

若环境未启动：

```bash
P31B_IMAGE_TAG=6b8772b scripts/p31b_env.sh start
```

如果需要从当前代码重新构建镜像，先执行 `scripts/p31b_env.sh build`，再执行 `start`；此时镜像标签会变为当前 HEAD 的短哈希。

验收环境的独立边界：

- 只使用 `product-knowledge-p31b` 项目、`knowledge_p31b` 数据库、Redis db 6 和独立命名卷。
- **不要**操作正式库 `knowledge`、正式容器 `product-knowledge-p11-*` 或旧验收容器 `p31-acceptance-api`。
- **不要**用 `docker compose down -v` 清理其他项目。

## 三、登录并创建品类

1. 浏览器打开 `http://127.0.0.1:18180/`。
2. 在登录页粘贴管理员令牌；令牌只保存在当前浏览器 `localStorage` 的 `p23.workbench.token`。
3. 登录后进入“管理员”，再打开 `http://127.0.0.1:18180/#/admin`。
4. 如果还没有品类，点击“新建品类”。
5. 填写品类编码与品类名称。编码只用于服务端作用域，创建后不能与已有编码重复。

注意：

- 普通售前令牌看不到管理员入口；即使手工输入 `/#/admin`，服务端仍返回 403。
- 不要复用正式环境的品类编码，也不要把正式数据写入本环境。

## 四、上传真实源码 ZIP

源码是建库的基础。没有已索引源码时，不能派生文档暂存快照。

### 1. 文件要求

- 只上传已获授权的 WAF 源码 ZIP。
- 文件内路径必须是相对路径，不能包含 `..`、绝对路径或符号链接逃逸。
- 单文件不超过 20 MiB，解压总量不超过 500 MiB；HTTP 上传上限 100 MiB。
- 不要包含生产密钥、证书私钥、客户数据或其他与产品知识无关的敏感文件。
- 排除目录可以保留，系统会记录排除项；但排除文件不会被当作已索引源码。

### 2. 上传步骤

1. 进入品类工作区的“概览与构建”。
2. 在“源码包”选择 ZIP，点击“上传为新快照”。
3. 上传成功返回 202 后，不要重复点击；等待 ingestion worker 解压。
4. 快照状态从 `uploaded`/`extracting` 变为 `extracted`。
5. 点击“构建 / 重建索引”，等待 index worker 完成。
6. 只有快照显示 `extracted/indexed` 才能继续。

### 3. 记录验收信息

记录以下信息交给验收负责人，不要记录令牌：

- 品类编码；
- 源码快照 ID；
- 源码 ZIP 的 SHA-256；
- 导入任务 ID、索引任务 ID；
- 文件数、排除数、总字节数；
- 快照最终状态与索引状态。

### 4. 常见失败

| 现象 | 处理 |
| --- | --- |
| 任务长期 `queued` | 检查 ingestion/index worker 是否运行，执行 `scripts/p31b_env.sh status` |
| `UNSAFE_PATH` | ZIP 含 `..`、绝对路径或非法条目；重新打包，不要绕过校验 |
| `INDEX_INTERNAL_ERROR` | 检查 `SOURCE_ROOT`/`INGESTION_ROOT` 与 index worker 日志 |
| `PermissionError` | 检查命名卷属主与 `/data` 目录权限，不要用 root 手工改库 |
| 镜像与代码不一致 | 确认 `P31B_IMAGE_TAG` 与当前代码提交一致，必要时重建镜像 |

## 五、派生文档暂存快照

文档修改不能直接发生在已发布快照上。

1. 确认当前源码快照为 `extracted/indexed`。
2. 在“概览与构建”的“文档暂存”区域点击“派生文档暂存快照”。
3. 系统创建 `derivation_type=document_update` 的派生快照，并复制现有文档。
4. 系统自动切换到该暂存快照，进入“技术文档”。

如果品类还没有生效发布，系统会回退到最近一次满足 `status=extracted`、`index_status=indexed`、`derivation_type IS NULL` 的源码快照。该回退不会伪造源码。

## 六、上传正式技术文档

### 1. 文件要求

- 只接受 DOCX、PDF、XLSX。
- 单文件不超过 20 MiB；服务端还会校验 MIME 与文件签名。
- 不要改扩展名伪装格式，不要把多个文档合并成一个不可解析的文件。
- 只上传已授权、与当前产品版本对应的正式技术文档。

### 2. 上传与解析

1. 确认当前快照为 `extracted + document_update`，页面显示“可编辑暂存”。
2. 在“技术文档”选择文件，点击“上传到暂存快照”。
3. 上传返回 202 后，文档进入解析队列。
4. 等待 `parse_status=parsed`；页面显示分段数、解析器版本、SHA-256 与大小。
5. 列表未更新时点击“刷新文档”，不要反复上传同一文件。

### 3. 替换、重解析与删除

- 同名文件不会覆盖旧文件；每次上传生成新文档、新存储键与新哈希，旧记录保留审计。
- 替换要求文件类型一致，否则返回 `DOCUMENT_REPLACE_TYPE_MISMATCH`。
- 只有派生暂存快照允许重解析；已发布快照返回 `DOCUMENT_STAGING_REQUIRED`。
- 被审核证据引用的文档不能替换、重解析或删除，返回 `DOCUMENT_IN_USE`。
- 解析失败保留 `parse_status=failed` 与错误码，不要直接改数据库。

### 4. 记录验收信息

记录文档数量、每个文档的 SHA-256、分段数、解析状态与解析任务 ID。不要记录文档全文或令牌。

## 七、重建索引与文档发现

1. 在暂存快照上点击“构建 / 重建索引”，等待 `extracted/indexed`。
2. 发起文档发现。
3. 当前未完成模型授权时使用 `structural` 模式：只做确定性结构发现，不调用外部模型。
4. 模型授权完成且服务端配置允许后，才可使用非 structural 的语义发现；前端不能覆盖服务端授权。
5. 发现只产生候选，不会自动发布。

注意：候选数量不是已接受能力数量；未审核候选不会进入发布清单。

## 八、能力审核

每个候选都必须人工逐字段审核：

1. 在“能力审核”选择候选。
2. 在证据检索区选择源码或技术文档段落，输入关键词检索。
3. 确认引文与上下文后点击登记证据；服务端重新读取来源并校验哈希，不信任前端摘录。
4. 填写 `name`、`action`、`target`、`business_goal`、`implementation_mechanism`、`supported_scope`、`limitations`。
5. 每个断言绑定已登记证据，标记“证据支持 / 证据不足 / 证据冲突”。
6. 填写人工核对说明，勾选“已核对文档引文范围”。
7. 点击“校验门槛”，按提示补齐字段、证据、声明类型、依赖关系与冲突。
8. 通过后“接受并生成修订”；不通过则“退回”或“拒绝”。

审核纪律：

- 文档明确写出的内容与推断内容必须区分；推断不能当作产品事实。
- 证据与描述不一致时选择冲突或不足，不能强行选择“证据支持”。
- 已接受修订不可原地修改；再次修改会生成新修订号。

## 九、发布前检查与发布

1. 进入“发布与回滚”，执行 release-check。
2. 检查是否至少有一个未发布的已接受修订，且所有能力门槛通过、冲突已解决。
3. 只有 `publishable=true` 时才能发布。
4. 勾选“我已核对覆盖缺口与发布范围”，填写发布说明。
5. 点击“发布当前审核清单”，在浏览器确认框中确认。
6. 发布成功后生成不可变 `Publication`，记录清单哈希、发布人、时间与能力数量。

发布后：

- 再次 release-check 返回 `publishable=false`，阻断项为 `NO_UNPUBLISHED_ACCEPTED_REVISION`，这是预期行为。
- 页面不提供强制发布或直接改指针的入口。
- 发布器会重新校验修订、门槛、冲突、覆盖确认与证据回读；证据不可读时失败关闭。

## 十、Gate 2 重新核查

管理员上传、审核、发布完成后，由验收负责人执行只读核查：

```bash
cd backend
P31B_IMAGE_TAG=6b8772b .venv/bin/python scripts/p31b_gate2_blocked.py
```

脚本只读管理员 API 与环境变量，不上传资料、不调用模型。它会重新识别：

- 非合成哈希、已索引的真实源码；
- 非合成哈希、已解析的真实文档；
- 服务器侧模型配置与企业授权；
- 非 structural 文档发现；
- 包含能力的真实发布物。

只有全部检查 PASS，Gate 2 才能判定 PASS。若仍显示 BLOCKED，按 `missing_inputs` 补齐，不要手工修改证据文件。

## 十一、Gate 3 交接

Gate 2 通过后，真实招标符合性评估才具备输入条件。当前 `scripts/p31b_gate3_tender_check.py` 只覆盖：

- 真实招标文件哈希与结构提取；
- 空白阈值保留；
- 无发布物时评估入口必须拒绝。

它**不会**在发布后自动给出 All/Some/None 结论，也不生成 Word/Excel 导出。Gate 2 通过后，必须由验收负责人按既有评估接口另行执行正向验收：

1. 使用真实招标文件创建提取任务。
2. 基于当前生效发布创建评估任务。
3. 等待 `taskworker` 完成。
4. 核对 All/Some/None 结论、逐参数证据与导出物。
5. 保存脱敏后的任务 ID、计数、结论分布与错误码；不要提交招标原文或导出全文。

在正向验收完成前，不得把 Gate 3 表述为 PASS，也不得宣称生产准确率。

2. 不把管理员令牌、数据库密码、对象存储密钥写入聊天、日志、截图或提交记录。

8. 不把合成样例结果当作真实 WAF 产品能力结论。

## 十三、故障处理

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 401 | 未登录或令牌缺失 | 重新粘贴管理员令牌 |
| 403 | 普通用户令牌或权限不足 | 使用管理员令牌，不要绕过前端 |
| 页面 502 | frontend 或 api 未健康 | 执行 `scripts/p31b_env.sh status`，查看 `logs` |
| 上传 413 | 超过上传上限 | 压缩或拆分文件，确认仍可解析 |
| 上传 422 `INVALID_MEDIA_TYPE`/`INVALID_SIGNATURE` | MIME 或签名不符 | 使用真实 DOCX/PDF/XLSX，不要改扩展名 |
| 上传 500 `PermissionError` | 存储目录属主不正确 | 检查命名卷与 `/data/tender`、`/data/exports` 权限 |
| 任务长期 queued | worker 未运行 | 启动 worker，检查心跳 |
| 解析长期未完成 | 解析任务失败或 worker 未运行 | 查看文档错误码与任务状态 |
| 派生失败 `DERIVATION_SOURCE_HASH_MISMATCH` | 排除项或历史快照不一致 | 使用本轮已修复版本；重建索引后重试 |
| 发布 409 | 期望生效发布 ID 或清单变化 | 刷新工作区，重新 release-check，不要重放旧请求 |
| 评估 409 `KNOWLEDGE_NOT_PUBLISHED` | 没有通过审核的生效知识库 | 完成审核与发布后再评估 |
| 模型步骤 BLOCKED | 模型未配置或企业授权未完成 | 由授权运维完成配置与授权，不要改前端 |
