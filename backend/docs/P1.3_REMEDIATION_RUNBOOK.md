# P1.3整改运行说明

## 数据分类先于模型

迁移0006为snapshot/document新增data_classification，历史与普通新上传默认enterprise。
调查请求旧data_classification只做审计兼容，不影响外发授权；任务创建和worker均从持久化来源读取。
源码或同快照任一文档为enterprise/未知，整个快照按enterprise决定外发。
BUILDER_ALLOW_ENTERPRISE=false保持不变，不能以选择bounded或请求public绕过。

人工样例测试：普通上传原有tests/fixtures/p13/knowledge_builder_source.zip与manual.md，
完成索引后，admin调用POST /api/v1/snapshots/{sid}/approve-public-fixture。
该入口不接受自定义分类字段，只核对服务端public_fixture_manifest.json的精确文件集合和原始字节哈希，
并再次回读实际文件；新增/修改源码或混入其他文档一律拒绝，成功记录管理员审计。
原企业资料不能用此入口任意降级。新上传的文档仍默认enterprise，原先public快照会按最高敏感级别拒绝出站。
审批过程中禁止在途任务；不提供任意public标签编辑入口。

## 推荐有限调查（本轮真实验收入口）

POST /api/v1/snapshots/{sid}/investigate:
`{"module_ids":["服务端模块ID"],"investigation_mode":"bounded","capability_limit":1,"include_equivalence":false}`。

保留旧explore模式和旧请求默认值以兼容既有接口；它仍存在大范围调查预算失败可能，
本轮验收与推荐运行一律显式bounded，不将历史explore效果声称为已修复稳定。
bounded最多读取本模块3个非敏感文本文件，各前80行；单微任务仅给一个文件片段。
模型只需输出紧凑能力、实现机制、限制及行号，通过Pydantic AI终端工具
register_evidence_and_candidate选择定位；服务端调用原read_source精确回读，
再register_evidence核验哈希，原子保存候选和链接，然后返回本地key。
不增加任意Shell/网络/写文件工具，也不执行源码。

先1条跑通；再capability_limit=2或3。include_equivalence=true仅在候选保存后，
单独用record_hypothesis生成possible_equivalent，始终hypothesis。
不保证必然存在等效性；必须人工判断假设是否合理。
每条候选先落库，后续超时/输出/预算失败，任务partial且保留先前候选；
POST /jobs/{jid}/retry复用检查点，已落库槽位不重复调用模型/插入候选，
失败段继续，预算仍跨任务尝试累计。已登记但尚未形成候选的证据可保留为审计记录。
coverage_incomplete始终true，模块succeeded仅表示有限任务已处理，并非覆盖全部入口。

## 真实验收

- `uv run python -m scripts.p13_remediation_acceptance --label 自定义唯一轮次名`
- 单能力通过后再运行
  `uv run python -m scripts.p13_remediation_acceptance --label 多候选唯一名 --count 3 --equivalence`
- 可用--module events/http/tests分别调查；未运行模块不能计漏报。
- 每轮JSON独立保存于reports/p13-remediation，已存在文件拒绝覆盖。
- 脚本使用真实API/队列/模型/PG，绝不注入FunctionModel；模型输出未经预置。
- 记录任务、来源分类、脱敏模型工具轨迹、输入/输出Token、耗时、未知费用，
  API再次回读证据哈希，并直接查询DB Claim/Link/Evidence记录。
- 脚本只使用固定人工源码与手册，不发送企业内容；不打印.env/容器全部环境。

当前模型仍为用户批准的glm-5.3-flash/low，4000响应Token/30000模块Token/8请求/30工具，
60秒请求/180秒模块上限；通过减小schema和输出轮次跑通，不自动切换模型或粗暴增额。
费用没有网关实际单价，始终null/unknown_not_zero；超时缺少用量时usage_incomplete=true。
