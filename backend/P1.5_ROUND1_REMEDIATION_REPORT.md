## 3. R01：发布冻结

### 3.1 问题

原 Probe 在读取已发布清单后，又按 `claim_revisions` 的“当前最大审核编号”重算修订。
管理员随后提交但尚未正式发布的新审核修订（包括 accept/modify/return/reject/merged），
会使 Probe 把仍然有效的已发布修订判为“已有更新审核”，隐藏能力并返回
`NEWER_REVIEW_NOT_PUBLISHED`。这违反了“已发布知识库在正式发布/回滚前保持冻结”的原则。

关系遍历中也存在同类的“最新 ReviewedRelation”判断，未发布的新关系审核可能影响
已发布关系是否可见。

### 3.2 根因

Probe 将“发布清单快照”与“审核表当前最新状态”混在一起判断。发布清单是发布时的冻结
快照，只有 `active_publication_id` 的正式切换才应改变读取结果；审核表后续变化不是读取
时重新计算发布内容的依据。

### 3.3 修复

- 删除 Probe 中基于最大 `ClaimRevision.number` 的修订新鲜度校验，以及
  `NEWER_REVIEW_NOT_PUBLISHED` 缺口。
- 保留并强化发布清单内的一致性校验：修订身份、所属能力、`decision=accept`、
  声明类型、内容、断言、可达性证据 ID 列表必须与清单一致；证据仍按同一快照复验
  哈希/引文/身份。异常继续返回 `PUBLICATION_REVISION_INVALID` 并 fail closed。
- 删除关系遍历中的“最新 ReviewedRelation”判断；保留关系身份、快照、`decision`、
  `details_json`、源/目标修订和关系类型的一致性校验，异常继续返回
  `RELATION_REVIEW_INVALID`。
- 未放宽发布审批：写入侧仍强制新发布使用最新接受修订和证据门槛，旧修订不能绕过审批；
  未发布审核不会被 Probe 自动采用。
- 读取结果仍绑定请求开始时的 `active_publication_id`/`active_snapshot_id` 和
  `publication_hash`；正式发布/回滚后下一个请求才切换。

### 3.4 测试

- 改写原“新修订必须隐藏旧批准”的不符冻结原则断言，改为
  `test_unpublished_review_does_not_change_frozen_publication`：
  accept/modify/return/reject 四种新审核后，Probe 仍返回 P1 的发布 ID、哈希、能力、
  修订与内容；新修订 ID 不出现在响应中；不再产生 `NEWER_REVIEW_NOT_PUBLISHED`。
- 新增 `test_new_publication_must_use_latest_accepted_revision`：
  新审核接受后，用旧修订发布被 422 `PUBLICATION_REVIEW_REQUIRED` 拒绝；用最新接受修订
  发布成功，Probe 切换到 P2。
- 新增真实 PostgreSQL 测试
  `test_probe_preserves_frozen_publication_until_publish_or_rollback`：
  P1 → 新审核修订已接受但未发布（仍 P1）→ 旧修订发布被拒 → 发布 P2 → Probe 切换 →
  回滚 → Probe 精确恢复 P1 的发布哈希与候选内容。

## 4. R02：覆盖信息隔离

### 4.1 问题

原 Probe 及普通 `GET /api/v1/capabilities` 直接返回发布时的完整覆盖对象，包含
未发布候选 ID（`unverified_assertions`）、内部审核/调查信息、待核验任务、未调查源码
文件清单、入口和文档片段明细。虽然这些是管理员定位覆盖缺口所需信息，但不应进入普通
读取契约。

### 4.2 修复

- 新增固定安全摘要 `coverage_summary`，只输出：
  覆盖是否完整、知识构建是否完成、语义覆盖状态、源码文件数、未调查文件数、未解释入口数、
  待核验/延后调查数、未验证断言数、未验证文档片段数、是否截断、`gap_types`。
- 摘要不包含 `snapshot_id`、`analyzed_ranges`、`uninvestigated_files`、
  `unexplained_entrypoints`、`pending`、`deferred`、`unverified_assertions`、
  `unverified_document_segments`、`note` 等明细字段。
- Probe 的 `coverage` 使用严格模型（额外字段拒绝），避免未来新增字段意外直出。
- 管理员仍可通过 `GET /api/v1/snapshots/{snapshot_id}/coverage` 读取完整覆盖详情；
  `GET /api/v1/capabilities` 对 admin 保留完整覆盖，对 read 返回摘要；read 访问显式
  快照覆盖详情仍返回 403。
- 保留 `coverage_incomplete`、`semantic_coverage`、待核验数量和缺口类型；
  `coverage_gaps_do_not_mean_unsupported`、`no_match_does_not_mean_unsupported`、
  `formal_compliance_decision=null`、`support_status=not_assessed` 均未改变。

### 4.3 测试

- 新增 `test_p15_probe_isolation.py`：
  - read Probe 的 `coverage` 键必须等于固定安全字段集合；未发布候选 ID、新审核修订 ID、
    唯一未发布内容标记均不出现在响应或 `unverified_gaps` 中。
  - admin 可读取完整 `/snapshots/{sid}/coverage`，其中包含未审核候选和文件明细；
    read 访问同一路径为 403。
  - admin 的 `/api/v1/capabilities` 保留完整覆盖；read 只能得到摘要。
  - admin Probe 也只返回安全摘要，不能通过管理员身份扩大 Probe 的字段暴露。
- 真实 HTTP 校验（使用 Compose 中的真实 read/admin 令牌）确认：read Probe 和 read
  capabilities 只含 12 个安全字段；admin capabilities 和 admin 快照覆盖含明细；
  read 快照覆盖返回 403。
