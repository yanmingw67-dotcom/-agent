### 3.4 双源冲突与归并

实现 `backend/app/knowledge/conflicts.py` 与 `backend/app/api/conflicts.py`：

- 未解决冲突阻断接受与发布；管理员裁决必须 `human_confirmed=true`，记录解释、裁决人、时间与审计事件。
- 不把支持范围与限制条件做并集；候选始终保留各自出处。

### 3.5 审核门槛来源等价

修改 `backend/app/knowledge/quality.py`：

- 每项断言必须有非测试源码或同快照有效文档证据；文档证据必须能解析回产品能力单元，引文必须与单元原文匹配。
- 文档单源需要四项显式确认：`proof_basis=document`、`document_scope_confirmed=true`、`availability_basis=document_declared|mixed`、`product_scope_confirmed=true`；混合源使用 `mixed`。
- 文档单源可豁免源码运行时接线；源码路径的接线、跨文件实现链、调用方证据等原有约束保留。
- 高风险措辞（隔离、原子、幂等、持久等）若由文档明确声明，按文档明示范围支持产品级能力，不强制伪造源码实现链；双源同样以文档明示范围为准。
- 新增扩大化措辞阻断：断言中出现“所有/全部/任意/零丢失/强事务/100%/全局一致”等，而文档引文没有对应表述时，返回 `DOCUMENT_SCOPE_EXPANSION`，不进入审核通过。
- 发布前 `publisher.validate_revision()` 重跑同一门槛，未解决冲突返回 `PUBLICATION_CONFLICT_UNRESOLVED`。

### 3.6 文档暂存更新与发布回滚

实现 `backend/app/knowledge/document_staging.py` 与 `backend/app/api/indexing.py`：

- `POST /api/v1/categories/{cid}/document-staging-snapshots`：从当前受控源码快照物理派生新暂存快照，新 `snapshot_id`、`derivation_type=document_update`；校验 manifest、归档哈希、物理文件哈希，复制源码归档并重新解压，复制文档文件与分段，不共享旧文件。
- `POST /api/v1/snapshots/{sid}/documents/{did}/replace`：在派生暂存快照内替换文档，重新解析/索引，写 `origin_json.replaced` 与旧文件哈希。
- `DELETE /api/v1/snapshots/{sid}/documents/{did}`：移除暂存文档及分段；被证据引用的文档返回 `DOCUMENT_IN_USE`。
- 已发布快照禁止直接修改，返回 `DOCUMENT_STAGING_REQUIRED`；旧发布、旧清单、旧物理文件在切换前保持不变。
- 新快照发布后旧发布仍可按 `publication_id` 回滚，清单哈希与证据精确复原。

### 3.7 Probe 兼容

`backend/app/retrieval/probe.py` 继续只读 P1.5 冻结发布：

- 文档证据可返回 `source_ref.document_id/segment_id`、`locator`、`quote`、`quote_hash`、`source_hash`。
- 原文件或分段哈希改变、文件删除时 fail closed，返回 `DOCUMENT_HASH_MISMATCH`、`SEGMENT_HASH_MISMATCH` 或 `EVIDENCE_SOURCE_UNAVAILABLE`，不继续把旧内容当可信证据。
- 未发布候选、内部覆盖明细、后台调查任务不进入普通 Probe 响应；保留 P1.5 安全 `coverage_summary`。

## 8. 原始失败与修复记录

1. **双源审核 422 `REVIEW_GATE_FAILED`**
   - 现象：混合证据断言进入高风险分支，返回 `DEPENDENCY_EVIDENCE_GAP`、`HIGH_RISK_IMPLEMENTATION_GAP`。
   - 原因：高风险分支只允许“无源码、仅文档”，混合源仍要求跨文件实现链。
   - 修复：文档存在时按“文档明示范围 + 严格范围确认”支持高风险产品级声明；源码单源路径保持不变。回归 P1.4 审核测试全部通过。

2. **暂存回滚测试比较重新生成的 DOCX 字节**
   - 现象：同一文档重新生成后 ZIP 时间戳不同，物理文件字节比较失败。
   - 修复：在替换前捕获旧文件原始字节，比较原文件是否保持不变，而不是比较重新生成的 fixture。

3. **暂存更新候选名称不一致**
   - 现象：测试按“策略模板导入”查找，实际候选名为完整句子。
   - 修复：按真实候选名“当前版本支持策略模板导入，模板由管理员维护。”审核与 Probe 断言。

4. **分段哈希测试改错对象**
   - 现象：修改文档第一个分段，但该分段未被断言引用，Probe 仍返回候选。
   - 修复：从审核修订的 evidence_id 追溯实际 segment_id 再篡改；并补充文件删除场景。

5. **文档范围扩大检查类型错误**
   - 现象：`documents` 已是证据字典列表，仍按 evidence_id 索引，触发 `TypeError: unhashable type: 'dict'`。
   - 修复：直接读取证据字典的 `quote` 字段，并补充扩大化断言阻断测试。

6. **规范检查**
   - 修复未使用导入、未使用局部变量、导入排序与格式化问题；最终 `ruff check` 与 `ruff format --check` 均通过。

### 10.2 R01：文档语义发现真实模型路径

- 提取字段包括功能名称、技术动作、功能对象、业务目标、支持范围、适用条件、明确限制、实现机制和声明类型；模型只收到服务端挑选的文档单元、`segment_id`、定位和分类，不收到可伪造的 `evidence_id` 或文件路径。
- 服务端不信任模型输出：锚点必须在当前批次内；引文必须逐字出现在对应分段（忽略空白差异）；一个候选的锚点必须属于同一文档；候选名称、技术动作和功能对象必须能回到引文（仅剥离“当前/旧版本、支持、部署、接入”等通用词）；支持范围、条件、限制必须逐字出现在引文中；扩大化词与性能数字必须出现在引文中；实现机制不在引文中时改为“文档未记录底层实现机制”的安全表述；非产品内容和证明材料/友商/控标/商务/未来规划/场景话术内容拒绝。
- 模型输出由 `SemanticCandidate`/`SemanticBatch` 的 Pydantic 严格模型校验，额外字段（如伪造的 `evidence_id`、文件位置、页码）会被拒绝；不接受模型直接创建证据。
- 证据由服务端按锚点 `segment_id` 回读并登记；`persist_candidates` 使用候选的全部锚点分段（`evidence_segment_ids()`），不再只登记主单元，且每个证据的 `supported_statement` 优先使用该锚点引文。`origin_json.extraction.anchors` 记录每个锚点自己的 `segment_id + locator`，不使用主单元位置冒充其他锚点。
- 授权与预算：`model_state()` 按可信分类检查 `builder_allow_synthetic`/`builder_allow_enterprise`，未授权返回 `UNAVAILABLE/DOCUMENT_DISCOVERY_MODEL_NOT_AUTHORIZED`；未授权时即使调用方注入测试模型也不会执行（防止以测试替身绕过外发授权）。真实端点复用 `app/agents/runtime.py::configured_model`，并受请求数、上下文长度、Token 和批次数限制。注入模型标记 `TEST_FUNCTION_MODEL` 或 `INJECTED_MODEL`，真实端点未调用时标记 `NOT_INVOKED`。模型模式发生预算/上下文/模型错误时，运行标记失败且不落纯结构候选，避免把降级结果误当模型能力。
- 审计只记录 payload/response 哈希、批次、Token 用量和错误类型，不落文档原文；审计事件不包含候选原文。
- 结构解析、噪声过滤和确定性候选仍保留为基础与降级路径；语义候选与结构候选按归一化名称合并，语义候选替换同名结构候选，其余追加，最后按候选限额截断。

自动化证据：`tests/integration/test_p16_semantics.py` 使用人工合成 DOCX/XLSX 和 `FunctionModel` 确定性替身，覆盖锚点伪造、引文不匹配、引文外名称/动作/对象（量子加密）、扩大化、性能数字、友商内容、跨文档锚点/证据和未授权注入模型拒绝执行。该测试只证明服务端校验与可执行管线，不证明真实模型质量。

**未验收项（必须明确）**：本轮没有可用的真实模型端点、企业文档外发授权或企业真实资料，因此没有向任何真实模型发送文档，也没有真实模型提取质量、时延、Token 成本或误报率结果。R01 的“真实授权模型”验收项标记为**未验收**，不能把 `FunctionModel`/确定性规则结果当作真实模型能力。后续接入时须单独授权、配置端点，并用合成复杂文档重新验收。

### 10.3 R02：双源语义匹配与冲突边界

重写 `app/knowledge/conflicts.py` 的匹配路径：

- 先做大小写/标点归一化、同义词归一化和通用前后缀剥离，再用字符双词相似度（阈值 0.66）和名称包含关系匹配不同措辞的同一能力。
- 对产品形态（硬件/软件/云端/单机/集群/控制台/命令行等）、组件（管理面/数据面/节点/数据库/API 等）、配置条件、支持范围进行比较；任一维度明确不相交时不误报冲突。
- 支持/排除判断同时看 `claim_type=exclusion` 和名称/动作/对象中的“不支持、不提供、禁止、无法、明确排除”等表述，避免动作字段已有排除但类型未标记时漏报。
- 只产生 `possible_duplicate`（风险 medium）或 `support_exclusion_conflict`（风险 high）；`details_json.match` 明确 `auto_merge=false`、`auto_resolve=false`、`requires_human_resolution=true`，不自动合并或裁决。不同来源但范围/条件不相交时不报重复。
- 未解决冲突继续阻断审核接受和发布；人工裁决、审核日志和发布前重校验行为保持原约束。

自动化证据：`tests/unit/test_p16_conflicts_semantics.py` 7 条通过，覆盖不同措辞同能力、支持/排除冲突、动作型排除、产品形态/组件差异、配置开关差异、范围/条件差异、同源不报双源重复；`tests/integration/test_p16_discovery.py` 13 条通过，真实 PostgreSQL 用例验证未解决冲突审核返回 422 `UNRESOLVED_CONFLICT`。

P1.6 新增的真实 PostgreSQL 综合用例 `test_staging_derivation_update_conflict_publish_and_rollback_on_postgres` 实际走通：

1. 创建品类和受控源码快照，上传并索引 DOCX/XLSX；
2. 文档发现产生支持/排除冲突；
3. 冲突候选审核返回 422 `UNRESOLVED_CONFLICT`；
4. 审核另一条无冲突能力并发布第一个清单；
5. 从当前生效（已发布）快照派生暂存快照；
6. 替换暂存 DOCX、重新索引，断言旧 DOCX 的 SHA-256 和物理字节不变；
7. 在新快照重新发现、审核并发布第二个清单；
8. 回滚到第一个清单，断言品类指针与发布清单恢复一致。

该用例不使用 SQLite 辅助函数 `set_active` 直接写 `active_snapshot_id`。真实 PG 的 `guard_active_snapshot` 要求 active 快照必须已发布且属于本品类，因此测试按真实业务顺序先发布、再派生；这也避免用测试捷径绕过业务约束。`INGESTION_ROOT` 与 `SOURCE_ROOT` 均指向临时目录，应用引擎通过测试内 connect 事件显式设置随机 schema 的 `search_path`，没有修改生产配置。

**本轮真实 PG 发现并修复的问题**：`document_staging.derive_staging_snapshot` 原先先以空 `archive_key` 插入快照，再在同一事务内更新为新 key；SQLite 不报错，但真实 PostgreSQL 的 `guard_snapshot_identity` 会把 `archive_key` 变化视为身份篡改并拒绝，导致派生 503。修复为在插入前生成 `archive_key`，让身份字段一次写入、不再更新；修复后上述真实 PG 综合用例通过。该修复未修改历史迁移。
